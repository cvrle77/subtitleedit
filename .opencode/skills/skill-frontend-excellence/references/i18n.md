# Internationalization and Localization

i18n is the engineering work that makes the product capable of being localized (extract strings, support bidi, use Intl): a codebase property. l10n is the per-locale content work (translate, vet, ship): a release artefact. Use this file when adding a locale, formatting per user preference, supporting an RTL script, debugging a translation-broken layout, or wiring hreflang.

## Translation pipeline UX

String extraction: the source is the catalogue, not the component.

- Every user-facing string lives in a resource file the translator can read, not in source code.
- Extract every string into a flat key namespace (`account.recovery.email_sent`) or a hierarchical structure the translation tool understands.
- Keys are stable; strings are translatable. Renaming a key invalidates every translation.
- Comments alongside the key give the translator context ("Button label on the recovery confirmation modal.").
- Screenshots attached to the key remove ambiguity for non-native engineers and translators.

Missing-key fallback by environment:

| Environment | Render |
|-------------|--------|
| Production | Default-locale string silently. Never the raw key (`account.recovery.email_sent`). |
| Development | The key in a high-visibility wrapper so engineers spot it (`[[account.recovery.email_sent]]`). |
| Staging | The key alongside the default-locale string so QA can confirm coverage before launch. |

Length expansion buffer (test with the longest reasonable translation, not the English original):

| Language | Length vs English |
|----------|-------------------|
| German | +30% on average; some technical terms +60% |
| Russian, Polish | +20% |
| Chinese, Japanese | shrink to ~70%, but glyphs are denser |

- Buttons reserve 30% extra horizontal room (a "Save" button at 60 pixels in English must fit "Speichern" at 80 pixels in German).
- Form labels wrap to two lines without breaking layout; labels next to inputs reserve the wrap height.
- Card titles allow at least one extra line: two-line max on every card, three on long-form locales.
- Table cells holding action labels grow with the label, not against it.

Coverage gate:

- A missing key in a locale fails the build or blocks the deploy; the pipeline reports missing keys per locale on every PR.
- A release candidate at 92% translation coverage ships at 92% only if the team has explicitly accepted the gap.

## Intl at depth

Use the `Intl` namespace as the standard instead of any project-specific date or number formatter. Constructors are cheap; memoise per locale.

### Intl.NumberFormat

Use for currency, percent, units, and decimal display. Locale-aware decimal separator, grouping separator, currency placement, and unit pluralisation come for free.

```js
new Intl.NumberFormat("de-DE", { style: "currency", currency: "EUR" }).format(1234.56); // "1.234,56 €"
new Intl.NumberFormat("en-US", { style: "percent", maximumFractionDigits: 1 }).format(0.078); // "7.8%"
new Intl.NumberFormat("en-US", { style: "unit", unit: "kilometer" }).format(42); // "42 km"
```

- The currency constructor takes a currency code (`USD`, `EUR`), not a symbol; the symbol is rendered per locale.
- Pick either fraction digits (`minimumFractionDigits` plus `maximumFractionDigits`) or significant digits (`minimumSignificantDigits` plus `maximumSignificantDigits`), not both.
- `useGrouping: false` disables the grouping separator (useful for IDs that look like numbers).

### Intl.DateTimeFormat

Use for any user-visible date or time. Pass an explicit `timeZone` for server-generated values; let the constructor infer the user's zone for client-side values.

```js
new Intl.DateTimeFormat("ja-JP", { dateStyle: "long", timeZone: "Asia/Tokyo" }).format(new Date());
// locale long date in Tokyo time
```

- `dateStyle` and `timeStyle` accept `full`, `long`, `medium`, `short` and pick a locale-appropriate ordering and separator.
- `era` (`short`, `long`) adds AD or BC, useful for historical content.
- `calendar` (`gregory`, `japanese`, `buddhist`, `hebrew`, `islamic`) overrides the locale's default calendar.
- For relative times ("2 days ago") use `Intl.RelativeTimeFormat`, not a string built from `DateTimeFormat`.

### Intl.PluralRules

Returns the plural category for a value in a locale: `zero`, `one`, `two`, `few`, `many`, `other`. English uses two, Arabic uses six.

```js
const pr = new Intl.PluralRules("ar");
pr.select(0);  // "zero"
pr.select(1);  // "one"
pr.select(2);  // "two"
pr.select(11); // "many"
```

Never write `count === 1 ? "item" : "items"`; it breaks on every locale with more than two categories. Use ICU MessageFormat, Fluent, or a key-per-category table.

### Intl.ListFormat

Joins items into a locale-aware list ("a, b, and c" in English; " et " between the last two items in French).

```js
new Intl.ListFormat("en", { style: "long", type: "conjunction" }).format(["red", "green", "blue"]);
// "red, green, and blue"
new Intl.ListFormat("en", { style: "long", type: "disjunction" }).format(["red", "green", "blue"]);
// "red, green, or blue"
```

Types: `conjunction` (and), `disjunction` (or), `unit` (no joiner, for unit lists). Styles: `long`, `short`, `narrow`.

### Intl.RelativeTimeFormat

Formats relative times in the user's locale with the right preposition and tense.

```js
new Intl.RelativeTimeFormat("en", { numeric: "auto" }).format(-1, "day"); // "yesterday"
new Intl.RelativeTimeFormat("en", { numeric: "auto" }).format(2, "hour"); // "in 2 hours"
new Intl.RelativeTimeFormat("fr", { numeric: "auto" }).format(-1, "day"); // "hier"
```

- `numeric: "auto"` gives the natural-language form ("yesterday"); `numeric: "always"` gives the numeric form ("1 day ago").
- Compute the delta and pick the unit (second, minute, hour, day, week, month, year) yourself; `RelativeTimeFormat` does the formatting, not the bucketing.

### Intl.Segmenter

Splits text into grapheme clusters, words, or sentences with locale-aware boundary detection. Critical for languages without spaces (Japanese, Chinese, Thai).

```js
const seg = new Intl.Segmenter("ja", { granularity: "word" });
const segments = [...seg.segment("これは日本語の文章です。")];
// each .segment is a word; .isWordLike distinguishes words from punctuation
```

The default `String.prototype.split(/\s+/)` is wrong for any CJK script. Use `Intl.Segmenter` for word count, locale-aware truncation, search highlighting, and sentence-level summarisation.

## Plural rules in depth

Plural categories per locale, from CLDR:

| Locale | Categories |
|--------|-----------|
| English | `one`, `other` (2) |
| French | `one`, `many`, `other` (3) |
| Russian | `one`, `few`, `many`, `other` (4) |
| Polish | `one`, `few`, `many`, `other` (4) |
| Arabic | `zero`, `one`, `two`, `few`, `many`, `other` (6) |
| Welsh | `zero`, `one`, `two`, `few`, `many`, `other` (6) |
| Japanese | `other` (1) |
| Chinese | `other` (1) |

Anti-patterns:

- `count === 1 ? "item" : "items"`: wrong on every locale with more than two categories.
- `count > 1 ? plural : singular`: wrong for zero, and for locales with a separate `zero` category.
- Concatenating "(s)": reads as a typo, does not translate.
- Picking the plural in code, not in the translation: the translator cannot fix what they cannot see.

Correct shape:

```js
const category = new Intl.PluralRules(locale).select(count); // "one", "other", "few", etc.
const message = strings[`cart.items.${category}`].replace("{count}", count);
```

Or ICU MessageFormat in the resource file:

```text
cart.items = {count, plural, =0 {Your cart is empty} one {# item} other {# items}}
```

ICU `=0` exact-match special-cases zero independently of the category; CLDR `zero` covers a different concept (some Slavic languages use `zero` for numbers ending in 0).

## Bidi correctness beyond dir="rtl"

Adding `dir="rtl"` to `<html>` swaps writing direction but leaves three classes of bug: mirrored icons, directional CSS properties, navigation order.

Mirrored icons:

- CSS mirror via a `dir` logical selector for a single flippable icon: `[dir="rtl"] .icon-chevron-back { transform: scaleX(-1); }`.
- Ship pre-mirrored SVG sets (`chevron-back-ltr.svg`, `chevron-back-rtl.svg`) and pick per direction when the visual asymmetry is meaningful (a hand-drawn arrow that does not reflect cleanly).
- Symmetric icons (search, settings, close) need no mirroring; audit the icon set once and mark the directional ones.
- Do not mirror: branded logos, country flags, content images, math notation, time-of-day icons (a clock face), media-control icons (play, pause, stop).

Logical properties (these flip with `dir="rtl"` automatically; directional properties do not):

| Directional (old) | Logical (new) |
|-------------------|---------------|
| `margin-left` | `margin-inline-start` |
| `margin-right` | `margin-inline-end` |
| `padding-left` | `padding-inline-start` |
| `padding-right` | `padding-inline-end` |
| `left: 0` | `inset-inline-start: 0` |
| `right: 0` | `inset-inline-end: 0` |
| `border-left` | `border-inline-start` |
| `text-align: left` | `text-align: start` |
| `float: left` | `float: inline-start` |

Navigation order in RTL:

- The back button lives on the right side of a top bar; the form's primary action lives on the left. The "back is behind me" mental model is mirrored.
- Replace hardcoded `position: absolute; left: 1rem` for a back chevron with `inset-inline-start`.
- In RTL the left arrow advances and the right arrow goes back. Bind keyboard handlers to logical concepts (`next`, `previous`), not physical keys, and route via the `dir` attribute.

Bidi isolation:

- Wrap user-entered content that may contain bidi characters (usernames, addresses, free-form titles) in `<bdi>` to isolate the embedded run from surrounding directionality: `<p>The author is <bdi>{userName}</bdi>.</p>`.
- For programmatic isolation in non-HTML contexts, wrap a string with the Unicode bidi isolate characters `U+2068` and `U+2069`.

## Locale-aware navigation

Arrow keys in a horizontal scroll container:

- LTR: right arrow advances, left arrow goes back. RTL: left arrow advances, right arrow goes back.
- Page Up, Page Down, Home, and End are logical and do not flip with direction.

Route arrow keys through a `dir`-aware adapter:

```js
const dir = document.documentElement.dir || "ltr";
const advance = dir === "rtl" ? "ArrowLeft" : "ArrowRight";
const reverse = dir === "rtl" ? "ArrowRight" : "ArrowLeft";
```

Carousels and forms:

- A carousel's next slide moves in the locale's reading direction, so in RTL the next slide enters from the left. Custom carousels must invert their swipe handlers per `dir`.
- Place Submit at the inline end and Cancel at the inline start using `flex-direction: row` with logical justification. Do not hardcode `justify-content: flex-end` or position buttons by left and right.

## hreflang and canonical interaction

The bidirectional rule: every locale references every other locale plus `x-default` for the fallback. Five locales means five `<link rel="alternate" hreflang>` entries on every page, one referencing the page's own URL. If page A references page B but B does not reference A, search engines drop the cluster: the cluster is symmetric or it is broken. (Deeper canonical treatment: see seo.md.)

```html
<link rel="alternate" hreflang="en-US" href="https://HOST/en/" />
<link rel="alternate" hreflang="de-DE" href="https://HOST/de/" />
<link rel="alternate" hreflang="ja-JP" href="https://HOST/ja/" />
<link rel="alternate" hreflang="x-default" href="https://HOST/en/" />
<link rel="canonical" href="https://HOST/en/" />
```

- The canonical chain: every locale page's canonical points at its own locale URL, not the default locale's. Cross-locale canonicalisation is almost always wrong.
- The exception: a duplicate-content page that should not rank in its own right (a print version, a `?utm=` variant) canonicalises to the indexable version. Default to "each locale canonicalises to itself."
- `x-default` is the best-guess fallback (typically the default locale, English) for a user whose locale is not in the set; it is a hint treated as one input among many.
- If the site uses geolocation to pick a locale, `x-default` should point at the locale-selection page, not at any specific locale.

## Translation-pipeline operational notes

Tool choice (pick by where the bottleneck lives):

| Tool | Strength | Weakness | Bottleneck |
|------|----------|----------|------------|
| Crowdin | In-context preview, translator-friendly | Per-string pricing scales fast | Translators |
| Lokalise | Strong CLI and API | Less polished translator UX | Engineers |
| Phrase | Versioning and branching parity with code | Heavier UI, learning curve | Localization managers |
| Open-source (Weblate, Pontoon) | Self-hosted, no per-seat fee | Requires ops capacity | Budget |

Format choice:

| Format | Strength | Weakness | Use when |
|--------|----------|----------|----------|
| ICU MessageFormat | Most expressive plural and select syntax, tooling support | Slight authoring complexity | Default |
| Fluent (Mozilla) | Multi-line, expressive, designed for translation | Smaller ecosystem | Grammatical agreement (gender, case) matters in many locales |
| GNU gettext (`.po`) | Massive ecosystem, every locale tool supports it | Limited plural syntax, poor select | Integrating with a legacy chain |
| Flat JSON | Trivial, works everywhere | Plural handling is per-key duplication | Simplest needs |

## Locale negotiation

Two signals: the `Accept-Language` header (passive, from the browser) and an explicit user choice (active, from a settings menu or URL prefix).

- An explicit user choice always wins; never override it with `Accept-Language`.
- Persist the choice in a cookie the server can read on the next request.
- The first visit (no cookie) uses `Accept-Language` to pick a default locale.
- If `Accept-Language` resolves to an unsupported locale, fall back to the default locale and surface the available locales prominently.
- The URL is canonical: locale lives in the path (`/en/`, `/de/`) or the subdomain (`en.` prefix). The cookie persists the choice; the URL communicates it.
- Never block on `Accept-Language` resolution; render the default locale immediately and switch after the cookie is read if needed.

## Currency display

Currencies share symbols across countries: `$` is USD, CAD, AUD, NZD, MXN and twenty more; `£` is GBP and EGP; `kr` is at least four currencies.

- Show the currency code alongside an ambiguous symbol on first reference ("USD$ 12.99", "CAD$ 12.99"); on second reference within the same view the symbol alone is enough.
- For prices in the user's own currency the symbol-only form is usually fine; the user already knows the currency.
- For prices that vary by region (a marketplace, a checkout flow), default to the disambiguated form everywhere.
- `Intl.NumberFormat` with `style: "currency"` and the right currency code does the right thing per locale; pass the code, not the symbol.

## Numbers in forms

| Separator | Locales | Renders 1234.56 as |
|-----------|---------|--------------------|
| Period | en-US, en-GB, ja-JP, zh-CN | `1,234.56` |
| Comma | de-DE, fr-FR, es-ES, pt-BR, ru-RU | `1.234,56` |
| Space / none | some technical contexts | grouping or decimal varies |

- Parse user numeric input in the user's locale using `Intl.NumberFormat.formatToParts` to expose the separators for reverse-parsing.
- Accept both decimal forms for copy-paste forgiveness; a user pasting `1234.56` into a de-DE form should not fail validation.
- On `<input type="number">` the browser handles locale-aware input itself; use `<input inputmode="decimal">` on text inputs for prices to bring up the right mobile keyboard.
- Store and transmit numbers as locale-neutral (period as decimal, no grouping); format only on display.
